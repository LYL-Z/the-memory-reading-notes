## 五、持续同步与“记忆”的明确协议

**每次新会话最先读**：本页 → `AGENTS.md` → `state/progress.json`、`state/next_actions.md` 的**最新开头** → `editorial/volume01-final-canon-and-volume02-handoff-2026-11-04.md` 的最新增补 → `editorial/volume02/2026-11-08-b2-first-24chapter-reading-order-v2.md` → 正在处理的**完整正文与审稿账** → 相应原库人物／事件／订正原页。**工作前重新核对 GitHub branch HEAD / PR状态**；禁止用本页的固定SHA代替新查询。

每次收到新的真实补充、作者否定、史料纠错或文学定稿意见时，依次：

1. 记下**作者原话、日期、来源、公开范围、涉及哪部哪章**；区分事实/记忆/他人说法/拟构/编辑建议。涉及其他人私密信息时，先停在受控渠道，不因“即时记忆”自动发布。
2. 核对既有人物、事件和时间轴；形成**增量订正账**，写明原表述、新表述和取舍理由；不抹除旧版对照，不补造其他人的动机。若原库需要写回，须有该库独立授权，不能把写本仓当成已更新原库。
3. 只有获准写作时才改正文；正文改动必须审事实、章节接缝、第一部重复、读者知情、公示边界与字数；第一部R50冻结不被普通“深精修”解锁。
4. **每次中断前同步更新** `state/progress.json` 和 `state/next_actions.md`；有重要裁决时新增日期化审稿或交接文档。用 `scripts/hanzi_count.py` 与相关校验器验证；记录状态、实际提交SHA、未完成事项。
5. 提交到**原有第二部 Draft PR #22** 的工作分支，检查远端HEAD仍符合预期，严禁强推／直接合并 `main`；核验GitHub端文件可读与PR继续为 Draft。未获授权的敏感原始文件、照片、完整私人对话不得为了“备份”放入公开仓库。

**能力边界**：GitHub 中的 `state/` 与交接档案可以成为**跨会话可重新读取的项目记忆**，但不是 ChatGPT 账号级长期记忆 API 的自动写入证明；下一次必须主动重新读仓库。会话结束之后也**不会后台自动监控或实时同步**，只有接到新消息并执行有权限的工具调用时才能推送。完成每次同步须报告：改了什么、哪个 PR／分支、确切提交SHA、哪些仍待作者或当事人确认。
