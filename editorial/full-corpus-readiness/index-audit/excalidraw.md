## 二、两份 `Drawing` 是不是空画布？——是，有结构证据

### 2.1 不靠解码也能判定

Excalidraw 插件导出的 `.excalidraw.md`，只要画布上有内容，就必然出现以下小节：

| 小节 | 何时出现 | 总图（有内容） | Drawing ×2 |
|---|---|:--:|:--:|
| `# Excalidraw Data` | 有内容 | ✅ `:13` | ❌ 无 |
| `## Text Elements` | 有文字元素 | ✅ `:15`（163 行） | ❌ **无** |
| `## Element Links` | 有节点跳转链接 | ✅ `:179` | ❌ **无** |
| `## Drawing` | 总有 | ✅ `:357` | ✅ `:10`（唯一小节） |

```bash
for f in *.excalidraw.md; do echo "### $f"; grep -n "^## \|^# " "$f"; done
```

**两份 Drawing 只有 `## Drawing` 一个空壳小节。** 没有 Text Elements、没有 Element Links、总字节 587（其中 frontmatter + 警告语就占了约 340 字节）。
→ **画布上 0 个文本元素、0 个链接。判定为空画布。**

### 2.2 顺带核实：payload 本身不可解，但**不能据此判为损坏**

两份文件的 `compressed-json` 段是 248 个字符（结尾 `A===`），去掉填充后 245 个数据字符。
标准 base64 的数据长度必须 ≡ 0/2/3 (mod 4)，**245 ≡ 1 (mod 4) 是不可能的**，任何标准解码器都会拒绝（我已用单字符删除＋单字符替换暴力穷举，均无法修复）。

**但是**——**总图的 payload 也解不开**（同样以 `===` 结尾，472-byte 量级同样 ≡ 1 mod 4）。

| 文件 | payload 字符 | 结尾 | 标准解码 |
|---|---:|---|:--:|
| Drawing 08-10 | 248 | `…uHmi4QEZkPcWPAQAA===` | ❌ |
| 总图 | 47,156 | `…` 同型 `===` | ❌ |

**总图是已知可用的正式画布**（57KB、163 行文字元素）。它和空画布**失败方式完全相同**，说明这是**Excalidraw 某个版本的编码约定**，不是文件损坏。

> **所以我不下「损坏」结论。** 只报事实：两份 Drawing 为空（结构判据），且两份同哈希（字节判据）。这两条不依赖解码。

## 三、这两份空画布：误建还是占位？

分开判，因为它们的来历不同。

### 3.1 `Drawing 2026-08-10 15.39.38.excalidraw.md` —— **占位性质的误建**

`Excalidraw索引.md` 末尾专门为它写了一段（`:25-27`）：

```
## 旧未命名图形
`2026-08-10未命名图形`尚未获得明确标题与叙事用途。
现保留原文件，不据内容推断人物或事件；待确认后再重命名并接入相应专题页。
```

**作者的意图是「保留，等以后想清楚用途再命名」。** 这是**占位**意图。

**但这段文字有两个硬伤：**

1. **它假设画布里有内容**（所以才说「不据内容推断人物或事件」）——而实测 0 元素。**索引在描述一个空的画布，好像里面画了东西。**
2. 「待确认后再重命名」——**空画布没有可确认的对象**。这个「待确认」永远不会到来。

**判定：这是「新建 → 打开 → 关掉 → 自动保存」留下的空壳，被索引善意地解释成了「待定用途的图形」。** 性质是**误建**，只是被文档升格成了占位。

### 3.2 `Drawing 2026-08-31 16.49.47.excalidraw.md` —— **纯误建（重复）**

| 判据 | 结果 |
|---|---|
| 与 08-10 同 MD5 | ✅ 完全相同 |
| 是否在 `Excalidraw索引.md` 中登记 | ❌ **未登记**（索引只列 总图 + 08-10） |
| 时间间隔 | 21 天 |
| 文件名 | Excalidraw 默认命名（`Drawing <时间戳>`），非人工命名 |

**判定：误建。** 21 天后再次「新建 → 关掉」，生成一份与 21 天前完全相同的空壳；两次都没有内容，也都没有被索引采纳（08-31 这份连索引都没进）。

> ⚠️ 注意一个反直觉点：**索引只登了 08-10，08-31 漏登**，看上去像「索引维护不到位」。
> 实际上**漏登是对的**——08-31 本来就是重复垃圾。
> 真正错的是「登了 08-10 当占位」。**索引错在多做了一步，而不是少做了一步。**

## 七、清理方案（**不执行**，供作者授权）

### 7.1 三档方案

| 档 | 动作 | 改动量 | 风险 |
|---|---|---:|---|
| **甲：只登记，不清理** | ① 索引补登 08-31 并注明「与 08-10 同哈希，空画布」② 改 08-10 的索引描述为「空画布（0 元素）」③ 总图 `:175` 去掉「无空文件、无重复哈希」两项或改为实测 | 3 处文字 | **0** |
| **乙：登记 + 页首加状态** | 甲 ＋ 在两份 Drawing 页首加一行状态注 | 5 处 | 0 |
| **丙：清理重复** | 乙 ＋ **删除 08-31**（纯重复空壳） | 5 处 ＋ 删 1 文件 | **需作者明确授权**（违反「不删文件」默认纪律） |

**建议甲或乙。不建议丙。** 理由：588 字节 × 1 份的成本远低于「删文件」这件事本身带来的流程风险；而且**保留 08-31 反而是一份证据**——它证明了「空壳会重复生成」，这是插件行为，不是人手滑。

### 7.2 具体文案（可直接用）

**① `Excalidraw索引.md` 末尾，替换现有的「旧未命名图形」一节：**

```markdown
## 空画布（2 份，同哈希）

| 文件 | 状态 |
|---|---|
| `Drawing 2026-08-10 15.39.38` | **空画布**：0 文本元素、0 元素链接 |
| `Drawing 2026-08-31 16.49.47` | **空画布**：与上者逐字节相同（MD5 `7fde4f40…`） |

两份均为 Excalidraw 默认命名的新建文件，未经绘制即保存。
**不据内容推断人物或事件**（无可推断的内容）。
如后续要画，建议另建具名文件，勿在此两份上续画——避免与索引快照混淆。
```

> 这段替换了原文「尚未获得明确标题与叙事用途…待确认后再重命名」——因为**空画布没有「用途」可确认**，留着这句话会让人一直等一个不会来的确认。

**② 总图 `:175`，改为：**

```
✓ 本图计数为 2026-08-13 快照，已过期；现行计数见 知识库总索引 §二（须带日期引用）。
  本图未执行全库完整性自检；空文件/重复哈希以 项目管理 的审计页为准。
```

**③ 总图 `:9` 与 `:20`，加日期限定：**

```
资料范围: 全库299个内容文件（2026-08-13 快照，已过期）
```

> 这是最小改动：**不改数字，只把「现在时」改成「当时时」**。因为重画总图上的文字元素代价很高，而加一个括号几乎零成本，却能阻止误引。

### 7.3 为什么不一刀切「全库重跑自检再更新总图」

因为总图 `:20` 的数字是**画在画布上的文字元素**，改它要打开 Excalidraw 改节点文本——工作量远大于收益。而 `知识库总索引 §二` 已经承担「带日期的现行计数」职能（见 `missing-dirs.md`）。
**正确分工：总图管结构关系（长期稳定），总索引管数字（须带日期）。总图不该承载计数。**
